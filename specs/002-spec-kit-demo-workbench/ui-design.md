# UI 设计：Spec Kit 演示工作台

## 设计目标

将应用首页改造为 `Team Spec Workbench`，让外部访问者在首屏理解项目是一个 AI 辅助的 Spec Kit 规范先行交付演示工作台。页面需要同时呈现项目定位、流程阶段、功能证据链和后续工作台能力预览。

界面应保持实用、清晰、面向任务，避免营销落地页风格。整体信息密度可以偏高，但必须保持良好的扫描性和移动端可读性。

## 页面结构

首页采用单页工作台结构，不新增路由。页面从上到下分为 6 个主要区域：

1. 顶部导航与项目标识
2. 首屏概览区
3. Spec Kit 流程时间线
4. Feature 证据区
5. 工作台能力预览区
6. 登录表单 evidence 区

## 顶部导航与项目标识

### 内容

- 左侧显示 `Team Spec Workbench`
- 右侧显示轻量导航锚点：
  - `流程`
  - `证据`
  - `任务`
  - `知识`

### 视觉

- 导航高度保持紧凑，使用底部分隔线。
- 背景与页面主体一致或略深，避免悬浮卡片感。
- 移动端导航可横向滚动或自动换行，但不能遮挡标题。

## 首屏概览区

### 内容

首屏左侧展示：

- 主标题：`Team Spec Workbench`
- 副标题：说明这是一个用于展示 AI 辅助 Spec Kit 工作流的开发工作台。
- 简短说明：强调每个功能都由规格、计划、任务和验证记录支撑。

首屏右侧展示摘要指标：

- 已完成 feature 数
- 当前 active feature
- Spec Kit 产物数
- 质量门禁状态

### 视觉

- 桌面端使用两列布局：说明区占较大宽度，指标区占较小宽度。
- 移动端改为单列布局，标题、说明、指标依次排列。
- 摘要指标使用紧凑卡片，每张卡片包含一个数字或状态、一行标题和一句解释。

## Spec Kit 流程时间线

### 阶段

必须按顺序展示 6 个阶段：

1. `Constitution`
2. `Specify`
3. `Plan`
4. `Tasks`
5. `Implement`
6. `Verify`

### 每个阶段展示内容

- 阶段名称
- 阶段目的
- 证据类型标签，用于区分项目级原则文档和当前 feature 产物
- 代表性产物或证据
- 当前项目中的对应状态

### 视觉

- 桌面端使用横向时间线或两行网格。
- 移动端使用纵向列表。
- 已完成阶段使用明确状态标识；当前 feature 尚未完成的阶段使用“进行中”或“待执行”。
- 不使用复杂动画，避免干扰信息阅读。

## Feature 证据区

### 内容

展示至少两个 feature 卡片：

- `001-login-form`：标记为已完成
- `002-spec-kit-demo-workbench`：标记为进行中

每张卡片展示：

- feature 编号和标题
- 当前状态
- 用户价值摘要
- 关联产物状态：
  - `spec.md`
  - `plan.md`
  - `tasks.md`
  - 验证记录

### 视觉

- 卡片使用 8px 或更小圆角。
- 已完成 feature 使用稳定的成功色标识。
- 进行中 feature 使用中性状态色标识。
- 产物状态以小型标签或列表展示，不能像按钮一样暗示可点击，除非实现真实链接。

## 工作台能力预览区

该区域展示 3 个模块，帮助访问者理解项目后续会扩展为团队项目管理与知识沉淀工具。

### Spec Browser

展示 feature 产物列表和状态摘要。

内容包括：

- feature 名称
- 产物数量
- 已完成产物
- 待补充产物

### Team Tasks

展示从 `tasks.md` 映射出的任务阶段看板。

列建议：

- 准备
- 基础能力
- 用户故事
- 验证

每列展示 2 到 4 条任务摘要。

### Knowledge Notes

展示需求决策、技术方案和验证复盘。

卡片类型：

- 决策
- 设计
- 验证

每张笔记卡片包含标题、类型和一句摘要。

### 视觉

- 桌面端使用三列或 2+1 网格。
- 移动端使用单列。
- 每个模块都需要明确标注为“演示预览”或“规划中”，避免让访问者误解为完整可编辑功能。

## 登录表单 evidence 区

### 内容

保留现有登录表单能力，用于展示 `001-login-form` 的实际交付结果。

区域应包含：

- 小标题：说明这是已完成 feature 的交付结果
- 登录表单本体
- 简短 evidence 说明：该表单对应 `001-login-form` 的 Spec Kit 产物

### 行为

登录表单保持现有行为：

- 邮箱必填和格式校验
- 密码必填和长度校验
- 记住我选项
- 忘记密码入口
- 提交中禁用按钮
- 模拟成功反馈

## 状态设计

### 已完成

用于 `001-login-form`、已存在的核心产物和已通过的质量门禁。

建议文案：

- `已完成`
- `已验证`
- `可查看`

### 进行中

用于 `002-spec-kit-demo-workbench` 的当前阶段。

建议文案：

- `进行中`
- `当前 feature`
- `待实现`

### 规划中

用于后续能力预览。

建议文案：

- `规划中`
- `演示预览`
- `后续 feature`

## 响应式要求

- 小屏宽度下所有主要区块改为单列。
- 指标、feature 卡片、任务列和知识笔记不得依赖固定宽度。
- 标题和长路径文本需要允许换行。
- 时间线在移动端必须使用纵向布局，避免横向挤压。
- 登录表单在移动端保持完整可用，输入框、错误提示和按钮不能重叠。

## 可访问性要求

- 页面使用语义化标题层级。
- 登录表单保留 `label`、`aria-invalid` 和错误提示关联。
- 状态不能只依赖颜色表达，需要同时有文字。
- 可交互元素需要有清晰焦点样式。

## 文案约束

- 页面和 README 使用中文作为主要文档和说明语言。
- 保留必要英文技术名词、命令、文件名和产品名。
- 页面和 README 不使用职业求职导向文案。
- 未完成能力必须标记为“演示预览”“规划中”或“后续 feature”。

## 视觉方向

### 色彩

建议使用中性深色或浅色工作台风格，搭配少量状态色：

- 主背景：深灰或近白
- 主文字：高对比中性色
- 成功状态：绿色
- 进行中状态：蓝色或青色
- 规划状态：灰色或琥珀色

避免让界面被单一色系主导。不要使用大面积紫色渐变、装饰性光斑或营销式 hero。

### 布局密度

- 首屏信息要完整，但不要拥挤。
- 区块之间使用清晰间距和分隔。
- 卡片只用于 feature、指标、任务和笔记等重复信息单元。
- 不使用卡片嵌套卡片。

## 实现提示

- `App.tsx` 负责页面编排和主要布局。
- `src/data/workbench.ts` 负责静态展示数据。
- `src/types/workbench.ts` 负责共享类型。
- `LoginEvidence.tsx` 负责承载当前登录表单逻辑。
- 其它组件按单一职责拆分，避免继续扩大 `App.tsx`。

## 审批检查点

实现前需要确认：

- 页面定位是否符合“Spec Kit 演示工作台”。
- 是否允许把登录表单从首屏主体调整为 evidence 区。
- 是否认可首页采用单页工作台结构。
- 是否认可静态数据驱动第一阶段 MVP。
