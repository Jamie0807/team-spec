# 研究：Spec Kit 演示工作台

## 决策：第一阶段使用静态数据驱动页面

**理由**：本 feature 的目标是对外展示 Spec Kit 流程和证据链，而不是构建完整的数据系统。静态数据可以让首页、证据卡片、任务看板和知识笔记稳定可演示，同时避免引入后端、文件读取或运行时 Markdown 解析。

**考虑过的替代方案**：

- 运行时读取 `specs/` Markdown：更自动化，但需要额外构建约束或文件解析逻辑，超出第一阶段范围。
- 后端接口返回 feature 数据：更接近真实产品，但会显著扩大范围。

## 决策：保留登录表单作为 evidence 模块

**理由**：`001-login-form` 已经有完整 Spec Kit 产物和已实现 UI，是展示“从规格到交付”的最好样例。将登录表单降级为 evidence 模块，既能保留既有功能，又能让默认首页表达更完整的工作台概念。

**考虑过的替代方案**：

- 删除登录表单：会丢失第一个真实功能示例。
- 让登录表单继续作为首屏主体：无法突出 Spec Kit 演示工作台定位。

## 决策：README 与应用页面共同承担对外展示

**理由**：README 适合解释仓库结构、流程和产物链接；应用页面适合快速展示工作台形态和流程可视化。两者结合可以覆盖“不运行项目”和“运行项目”两种访问方式。

**考虑过的替代方案**：

- 仅强化 README：交互和产品感不足。
- 仅强化应用页面：仓库访问者不运行项目时难以理解产物结构。

## 决策：不新增依赖

**理由**：当前 UI 可以用 React、TypeScript 和 Tailwind CSS 完成。新增组件库或图标库会增加维护成本，也不符合第一阶段公开展示 MVP 的范围。

**考虑过的替代方案**：

- 引入 UI 组件库：能加快组件拼装，但会弱化本项目已有技术栈的一致性。
- 引入图标库：视觉更丰富，但不是本阶段必需能力。

## 决策：实现前需要 UI 设计审批

**理由**：本 feature 改造默认首页和多个工作台模块，属于明显 UI 变更。项目宪法要求 UI 设计必须在实现前获得人工审批。

**考虑过的替代方案**：

- 直接编码实现：会违反项目宪法中的人工审批门禁。
